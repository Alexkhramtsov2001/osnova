## Экономный режим работы Codex

1. По умолчанию работайте в экономном режиме, выполняйте только действия, необходимые для конкретной задачи.
2. Перед изменениями определяйте минимальный набор затронутых файлов. Не читайте весь репозиторий без необходимости.
3. Не запускайте полный набор тестов, линтеров, сборок и проверок TypeScript после каждой небольшой правки.
4. Для небольших изменений выполняйте только релевантные проверки. Для изменений логики запускайте соответствующие тесты.
5. Полную сборку и комплексное тестирование выполняйте при существенных изменениях, перед релизом либо по прямому запросу пользователя.
6. Не повторяйте успешные проверки без изменений кода или других обоснованных причин.
7. При ошибке анализируйте конкретную причину, а не запускайте все проверки повторно.
8. Ограничивайте вывод команд необходимой диагностической информацией. Не выводите огромные логи без необходимости.
9. Не ожидайте завершения GitHub Actions, если пользователь прямо не запросил проверку CI.
10. Не выполняйте автоматические повторные попытки GitHub Actions.
11. Сначала вносите изменения в реальные файлы проекта, затем проводите соразмерную проверку результата.
12. Не проводите масштабный аудит, рефакторинг или изменение архитектуры без отдельного запроса.
13. Коммиты и обычный push только с документацией репозитория сайта заранее разрешены владельцем. Для остальных коммитов и отправки недокументационных изменений в GitHub требуется прямое указание пользователя.
14. В конце задачи кратко сообщайте, какие файлы изменены, какие проверки выполнены и что осталось непроверенным.
15. Если проверка необходима для безопасности или корректности изменений, не пропускайте её только ради экономии токенов.

## Стратегия локальных проверок

1. При изменении текста, CSS, цветов, отступов и других визуальных параметров проверяйте diff и при необходимости затронутый файл. Не запускайте полную сборку и весь набор тестов автоматически.
2. При изменении React-компонентов запускайте ESLint только для изменённых файлов: `node ./node_modules/eslint/bin/eslint.js <изменённые-файлы>`, а также релевантные тесты, если они существуют. Script `lint` выполняет `eslint .`, поэтому `npm run lint -- <файлы>` не ограничивает проверку этими файлами.
3. При изменении TypeScript-логики запускайте `npm run typecheck` и соответствующие Vitest-тесты через `npm test -- <пути-к-тестам>`. Не запускайте Playwright без необходимости.
4. При изменении калькулятора стоимости, генератора чертежей и других важных алгоритмов запускайте целевые модульные тесты через `npm test -- <пути-к-тестам>`. Используйте Playwright через `npm run test:e2e -- <пути-к-тестам>`, когда изменены пользовательские сценарии, требующие браузерной проверки.
5. Полную последовательность `npm run lint`, `npm run typecheck`, `npm run format:check`, `npm test`, `npm run test:e2e` и `npm run build` запускайте перед релизом, при крупных изменениях или по прямому запросу пользователя.
6. Не используйте `test:watch` для разовых проверок; script `test` уже выполняет `vitest run` без наблюдения за файлами.
7. Не запускайте тесты в цикле и не повторяйте успешные команды без изменений кода.
8. Не устанавливайте зависимости повторно, если существующее окружение исправно.
9. При запуске тестов ограничивайте вывод необходимой информацией. При ошибках показывайте конкретные причины.
10. Если проверка пропущена ради экономии, кратко сообщайте об этом пользователю.
