## 1. Как выполнять

Одна карточка — один запрос владельца. Не выполнять следующую автоматически. Читать корневой/локальный AGENTS, текущий локальный PROGRESS, карточку и только её контракт. Нужны цель/вход-выход/ошибки/файлы/тесты до кода. Обычно 1–5 файлов и один контракт; если ожидается более примерно 400 строк существенного изменения или несколько самостоятельных операций, сначала разделить карточку на .1/.2 с отдельными зависимостями и прежним общим критерием. Ограничение размера — ориентир планирования, не повод обрезать нужный тест.

119 исходных карточек не означают 119 поручений на код. C09/C12/C13 разделены на письменный контракт .1 и реализацию .2, C11 — на generate .1 и раннюю проверку .2; дочерние зависимости обязательны, родитель завершается только после всех его подзадач. Поздние F/G/H — малые контракты будущих возможностей; перед реализацией каждой крупной операции их уточняют/дробят отдельно. Этим планом не обещается заранее полностью спроектированный AutoCAD.

## 2. Команды проверок

Сверять с фактическим package.json генератора. Следующие профили — часть каждой карточки; это процедуры, не новые scripts. Script check отсутствует; script backup реализован локально в B13. Зависимости не переустанавливать без причины.

- **P-core:** `pnpm run typecheck:core`; `pnpm test -- tests/unit/<названный-тест>.test.ts`; точечный `node node_modules/eslint/bin/eslint.js <изменённые.ts>`. Заменить пути реально созданными файлами; для Node-адаптера дополнительно проверить типы затронутого tools-кода. Нужны границы/отказы/frozen input, не тест собственной константы чтением той же константы.
- **P-ui:** `pnpm run typecheck`, точечный ESLint, связанные unit-тесты. Перед preview/e2e нужна актуальная `pnpm run build` только генератора; затем `pnpm run test:e2e -- <названный-тест>.spec.ts`. Если тот же build уже актуален, не повторять. Реально просмотреть адресные скриншоты.
- **P-gate:** `pnpm run lint`, `pnpm test`, `pnpm run build` (включает typecheck), `pnpm run test:e2e`, `pnpm run format:check` отдельного генератора; специальные seeded-прогоны по VALIDATION_TESTING. Сайт не запускать до E. Успешные области после исправления повторно не гонять без причины.
- **P-contract:** небольшая документированная спецификация/ручные примеры/лицензионный или форматный образец; до кода уточнить профиль команд по актуальному окружению. Отсутствующий код не считается проверенным.
- **Документация:** Prettier изменённых Markdown, локальные ссылки, зависимости/ID и diff. Unit/E2E/production build не нужны. Не менять конфиги ради исключения неудобного документа.
- После любой кодовой задачи — diff/whitespace, локальный PROGRESS с фактическими командами/числами/ограничениями. Ошибки сначала объяснить, не запускать весь набор по кругу.

## 4. Границы Git и резервных копий

Документация в github-checkout commit/push разрешена заранее. Код/тесты генератора пока локальны, remote отсутствует; отправка документации не включает их. Q01 после отдельного подтверждения может разрешить ранний отдельный тестовый remote/стенд до полной v1; это явное исключение владельца, не автоматическое следствие нового плана. До согласия не создавать remote/deploy. Публикация основного сайта не разрешена этой задачей.

До больших изменений сохранять резервную копию. B13 выполнен локально: pnpm run backup / node scripts/backup.mjs поддерживает create/verify/restore в новую папку; точный синтаксис — локальный README. После контрольных точек и в конце рабочего дня делать/проверять резервную копию вручную в рамках активной работы; это не фоновая автоматизация. Проверка восстановления обязательна, Git не заменяет её. В backup не включать node_modules/dist/.git, секреты, полные логи и производные тестовые артефакты.
