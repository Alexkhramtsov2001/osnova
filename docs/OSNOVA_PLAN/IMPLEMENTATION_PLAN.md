Дата: 20.10.2026. Статус: **B01 выполнен локально; B02 и последующие задачи не начаты**. Результаты B01 и реальные команды сохранены в `osnova-main/osnova-plan/PROGRESS.md`, вне репозитория сайта. Требования к результату — в [V1_SPECIFICATION.md](V1_SPECIFICATION.md), крупные выпуски — в [RELEASE_PLAN.md](RELEASE_PLAN.md). Этот документ заменяет порядок работ архивной `docs/13_ROADMAP.md` и требование читать полное ТЗ/собирать весь сайт на каждой задаче из архивного протокола. Корневой AGENTS.md и прямые указания владельца сохраняют приоритет.

## 1. Готовность и граница определённости

Для продолжения после каркаса B01 имеются продуктовые границы, ограничения калькулятора, численные допуски, каталоги помещений/стен/мебели, правила проёмов/лестницы, топологии, бюджеты, требования редактора, хранения, PDF, сметы и офлайн. Выбраны и испытаны основные доноры. Нового широкого поиска библиотек перед B02 не требуется.

Не доказаны работа адаптера OSNOVA, успешность собственного поиска, производительность, 30 положительных задач с эталонами и браузерная совместимость PLAN. Это результаты будущих задач, а не неизвестные предпочтения, которые владелец должен угадать заранее. Нельзя гарантировать отсутствие ошибок до написания и проверки кода. Если донор не проходит конкретный контракт, приостановить только зависимые задачи и исправить/заменить необходимый модуль; не переписывать всё приложение и не ослаблять требования молча.

Подробно разложена первая версия B–E. После неё приведены последовательности расширений F/G и исследовательская граница H. Новые функции позднего выпуска сначала получают собственный контракт и фикстуры; нельзя сейчас считать все алгоритмы будущего CAD окончательно определёнными.

## 2. Изолированное место разработки

Отдельное приложение создано в соседнем каталоге `osnova-main/osnova-plan`, **вне `github-checkout`**, в собственном локальном репозитории без коммитов и remote. Прямое указание владельца: новый код и проверки остаются только на ПК до почти полной готовности v1; интеграция будет значительно позже. Не добавлять исходники в репозиторий сайта и не выполнять публикацию/отправку. Даже достижение готовности само по себе не разрешает push без прямого поручения.

Причина изоляции проверена по текущей конфигурации сайта: `lint` запускает `eslint .`, Vitest без отдельной конфигурации может обнаруживать новые тесты, а форматирование обходит репозиторий. Простое добавление второго приложения внутрь сайта могло бы расширить его проверки до этапа интеграции. Соседний проект позволяет не менять AGENTS.md, CI, package.json и исходники сайта ради раннего прототипа.

Пути ниже относительны новому проекту. По решению B01 чистые domain/geometry/validation/generation/commands размещаются внутри `src/core`, с публичной точкой входа `src/core/index.ts`; браузерные worker/persistence/export-адаптеры и `src/ui` остаются снаружи. Это границы ответственности, не требование создать все пустые каталоги заранее. Ядро отдельно проверяется TypeScript без DOM/Node ambient types и ограничениями импортов ESLint; оно не импортирует React, IndexedDB или страницы сайта. В E оно подключается как локальный пакет/сборка без второй копии React и без копирования разошедшихся исходников.

## 3. Размер одной задачи и порядок продолжения

- **Один запрос владельца — одна задача с ID**, а не весь этап B/C/D/E. Следующие строки автоматически не выполнять. Нужную зависимость без готового результата нельзя заменить заглушкой, объявленной рабочей функцией.
- Обычный объём — одна функция/контракт или один пользовательский шаг и примерно 1–5 связанных файлов. Это ориентир: если задача существенно больше, до правок разделить её на `.1`, `.2` и сохранить прежний общий критерий завершения. Не дробить проверяемую атомарную операцию ради формального числа файлов.
- В начале: AGENTS.md, текущий Git status/diff, строка задачи, указанные разделы спецификации и только затронутые исходники/тесты. Не перечитывать весь архив, исследование OSS и сайт при каждом продолжении.
- До правок определить минимальные файлы, вход/выход, ошибки и проверку. Новое неоднозначное поведение сначала кратко закрепить в контракте соответствующей функции; существующие правила без причины не пересматривать.
- Писать реальный код и содержательные проверки по мере появления функций. Не создавать наперёд десятки пустых модулей, фиктивные успешные ответы и тесты, повторяющие реализацию.
- Зависимости устанавливать один раз при B01/B05 и только при реальной необходимости позднее. Не запускать повторно успешные команды без изменений, не использовать watch для разовой проверки, ограничивать логи диагностикой.
- Математика/логика: типы и целевые unit/contract-тесты. UI: ESLint затронутых файлов, типы и адресный браузерный сценарий. Новый bundler/Worker/export/PWA: сборка **отдельного генератора**, если это необходимо для проверки пути ресурсов. Полный сайт не проверяется до интеграции E.
- Scripts отдельного проекта подготовлены в B01 и перечислены в его локальном README; запускать их из `osnova-plan`, не подменять командами сайта. При будущих изменениях сверять с его актуальным package.json. Документационные задачи требуют проверки форматирования и diff, без тестов или сборки.
- При падении разбирать конкретную причину, исправлять в рамках текущей задачи и повторять только затронутую проверку. Не маскировать регрессию удалением старого теста, увеличением допусков или отключением валидации.
- Не создавать commit/push без указания; локальные изменения сохранять. Не ждать CI и не перезапускать его автоматически.

Каждая задача считается завершённой только после получения указанного результата и соразмерной проверки. Если лимит сессии исчерпан, честный статус `in_progress`: перечислить готовое, невыполненное и точный следующий шаг. Не начинать следующую задачу, не помечать текущую готовой только потому, что код написан.

После кодовой задачи обновлять **PROGRESS.md отдельного генератора**: ID/статус, изменённые файлы, команды и результаты, известное ограничение, следующая разрешаемая задача. Не складывать туда полные логи, копии репозитория и чувствительные данные. В новом чате достаточно ID, этой записи, diff и связанного контракта; не полагаться на память старого чата. Журнал создан в B01 и остаётся локальным.
