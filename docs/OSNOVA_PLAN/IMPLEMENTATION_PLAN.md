Одна карточка — один запрос владельца. Не выполнять следующую автоматически. Читать корневой/локальный AGENTS, текущий локальный PROGRESS, карточку и только её контракт. Нужны цель/вход-выход/ошибки/файлы/тесты до кода. Обычно 1–5 файлов и один контракт; если ожидается более примерно 400 строк существенного изменения или несколько самостоятельных операций, сначала разделить карточку на .1/.2 с отдельными зависимостями и прежним общим критерием. Ограничение размера — ориентир планирования, не повод обрезать нужный тест.

119 исходных карточек не означают 119 поручений на код. C09/C12/C13 разделены на письменный контракт .1 и реализацию .2, C11 — на generate .1 и раннюю проверку .2; дочерние зависимости обязательны, родитель завершается только после всех его подзадач. ## 2. Команды проверок

Сверять с фактическим package.json генератора. Следующие профили — часть каждой карточки; это процедуры, не новые scripts. Script check отсутствует; script backup реализован локально в B13. Зависимости не переустанавливать без причины.

- **P-core:** `pnpm run typecheck:core`; `pnpm test -- tests/unit/<названный-тест>.test.ts`; точечный `node node_modules/eslint/bin/eslint.js <изменённые.ts>`. Заменить пути реально созданными файлами; для Node-адаптера дополнительно проверить типы затронутого tools-кода. Нужны границы/отказы/frozen input, не тест собственной константы чтением той же константы.
- **P-ui:** `pnpm run typecheck`, точечный ESLint, связанные unit-тесты. Перед preview/e2e нужна актуальная `pnpm run build` только генератора; затем `pnpm run test:e2e -- <названный-тест>.spec.ts`. Если тот же build уже актуален, не повторять. Реально просмотреть адресные скриншоты.
- **P-gate:** `pnpm run lint`, `pnpm test`, `pnpm run build` (включает typecheck), `pnpm run test:e2e`, `pnpm run format:check` отдельного генератора; специальные seeded-прогоны по VALIDATION_TESTING. Сайт не запускать до E. Успешные области после исправления повторно не гонять без причины.
- **P-contract:** небольшая документированная спецификация/ручные примеры/лицензионный или форматный образец; до кода уточнить профиль команд по актуальному окружению. Отсутствующий код не считается проверенным.
- **Документация:** Prettier изменённых Markdown, локальные ссылки, зависимости/ID и diff. Перед commit/push из `github-checkout` обязательно выполнить точную проверку CI `npm run format:check` (`prettier --check .`). Markdown parse или вызов форматтера без сравнения результата эту проверку не заменяют. Форматировать только указанные в ошибке файлы, не менять конфиги и исключения ради прохождения. Unit/E2E/production build для чистой документации не нужны.
- После любой кодовой задачи — diff/whitespace, локальный PROGRESS с фактическими командами/числами/ограничениями. Ошибки сначала объяснить, не запускать весь набор по кругу.

### 7.2. Проверяемые будущие срезы

После возврата по §7 сначала выбрать один следующий срез и разделить его на «контракт → ограниченная реализация → независимые проверки». Весь список не является заданием на один запрос:

1. **Ручной дом с пустого участка.** Один плоский участок и небольшой поддержанный дом: фундамент, стены, перекрытие/пол, крыша, окно и дверь. Создать без генератора/ИИ, изменить размер, отменить и повторить изменение, сохранить и открыть заново. Проверить ID, размеры, связи и сохранность незавершённого черновика. Профиль конструкций сначала ограничить контрактом.
2. **Согласованный 3D-редактор и прогулка.** Тот же проект; реальный проём и проход, камера, несколько материалов/слоёв. Правка из 3D видна в 2D и наоборот, Undo общий; сравнить известные размеры. Отдельно проверить наружный объект участка. При нехватке ресурсов проект остаётся доступен.
3. **Мебель, свой ресурс и этапы.** Добавить предмет из каталога и поддержанный импорт, задать габариты, заменить текстуру, сохранить/открыть без исходной папки. Переключить стадии одного дома и убедиться, что скрытие не меняет его данные. Повреждённый ресурс и изменение ранней конструкции не дают ложного готового результата. Импорт и стадии получают отдельные подзадачи.
4. **Генератор и помощник в ручном проекте.** Явно выбрать, что разрешено менять; закреплённые и ручные части сохраняются. Предложенный вариант проверяется, сравнивается и применяется либо отменяется. Для поисковой роли ИИ отдельно доказать выигрыш покрытия/разнообразия/работы при одинаковом бюджете; красивое изображение и успешный текстовый N01 это не доказывают. Создание предметов моделью — отдельный условный опыт, после устойчивого импорта.
5. **Игровой сценарий.** Только после устойчивой основы проверить одно ограниченное задание с условным бюджетом и прогрессом строительства, сохранением и возвратом в творческий режим. Развитие до полной игры рассматривается по результату; сетевой режим, подписки, сложная физика и тяжёлый рендер не добавляются автоматически.

Для каждой будущей контрольной точки нужны сквозной пользовательский сценарий, сохранение/повторное открытие, проверки ошибок и Undo, фактический просмотр 2D/3D и измерение ресурсов. Успешная геометрия, удобство редактора, визуальная реалистичность и инженерная пригодность принимаются раздельно. Срезы не меняют сегодняшние зависимости F/G/H или N; перед Desktop их сопоставляют с уже реализованным, чтобы не писать готовые части повторно.
