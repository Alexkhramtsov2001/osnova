## 3. Калькулятор и PLAN: общее рабочее пространство

Согласовано владельцем 28.10.2026. Это будущий контракт этапа E, а не описание работающей интеграции. Текущий кодовый шаг генератора остаётся C16.2; U/D/R/S/E и разрешения на публикацию выполняются в своём порядке. Отдельный локальный PLAN до E сохраняет самостоятельность.

### 3.1. Один проект и три представления

Целевой интерфейс в одной вкладке браузера: **«Параметры → Планировка → Смета»**. Переключение меняет представление текущего рабочего проекта, сохраняя введённые значения и выбранный вариант. Это внутренние представления приложения; открывать отдельную вкладку браузера для обычного перехода не требуется.

На экране «Параметры» находится единственная форма генерации, встроенная в калькулятор. «Планировка» отдаёт основную площадь чертежу и показывает компактную сводку снимка для чтения. Для изменения входа сводка возвращает в поле калькулятора. «Смета» показывает предварительный расчёт и настройки стоимости. Все представления читают один рабочий контекст.

На desktop допускаются панель свойств и чертёж рядом. На планшете и телефоне панель раскрывается отдельно, а формы и план не сжимаются в две узкие колонки. Краткая сводка сообщает текущую площадь, технологию, состояние плана и основание отображаемой стоимости. Переключатели, раскрытия и действия доступны с клавиатуры; фиксированные панели не перекрывают чертёж и кнопки. Размеры и режимы взаимодействия берутся из SPECIFICATION §10.

Существующие страницы каталога, проекта, калькулятора и кабинета сохраняют свои входные сценарии. Конкретные маршруты и адреса представлений определяются на E03; названия представлений не означают создание маршрутов сейчас. Старые прямые ссылки и browser back/forward сохраняют работу.

### 3.2. Общий черновик и владельцы данных

Общность данных относится к **текущему рабочему черновику**. Сохранённая смета, принятый план и исходный импорт остаются версионированными снимками.

| Данные                                               | Владелец и правило                                                                                                              |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Желаемые параметры дома и настройки текущего расчёта | Один контроллер рабочего черновика. Обе панели редактируют одни и те же значения, а не синхронизируют две самостоятельные формы |
| Текст ещё невалидного поля                           | Общее состояние редактирования формы. Не заменяет последний валидный нормализованный ввод и не считается применённым параметром |
| Комнаты, цели, вход и пожелания                      | Данные PLAN, связанные с общими параметрами дома; комнаты не вычисляются из цены                                                |
| Стены, проёмы, фактические площади и доступ          | Канонический PLAN Project. Чертёж и цифры не редактируются параллельно как независимые модели                                   |
| Принятый вариант плана                               | Свой снимок Project/revision, вход, профиль и версии проверки; исходные данные генерации доступны для сравнения                 |
| Предварительная стоимость текущего черновика         | Производное существующего калькулятора по актуальным валидным параметрам и его версии каталога                                  |
| Сохранённая смета                                    | Отдельная существующая запись с ID и исходными параметрами. Обновление рабочего черновика её автоматически не переписывает      |
| Геометрическая ведомость и смета PLAN                | Будущий результат R по конкретному снимку геометрии; не подмена быстрой калькуляторной оценки                                   |

На E04.1 закрепить типизированный контракт связи: идентификатор рабочего контекста, ссылка на PLAN Project/revision при наличии, источник manual/calculator/catalog, sourceProjectId/sourceEstimateId при наличии, версии ограничений и каталога, текущие параметры, ревизия геометрического ввода, ревизия настроек цены и ссылка на выбранный вариант. ID проекта каталога, ID PLAN Project и ID сметы различаются по смыслу. Отсутствующий ID не придумывается.

Рабочая оболочка связывает существующие записи и хранит текущий ввод; она не становится вторым каноном здания. Конкретные TS-типы и границы транзакций описываются на E04.1 до кода. Общая версия рабочего черновика не подменяет Project.revision, Worker requestId/baseRevision или CAS сохранения.

Снимок происхождения захватывается при явном выборе источника. Каждый ввод числа, переход между представлениями или возврат из истории не создаёт новый origin и не переопределяет исходный baseline. Связь с новой сохранённой сметой не переписывает происхождение уже принятого плана.

### 3.3. Что автоматически влияет на планировку

Общий чистый адаптер ограничений появляется на E02 с limitsVersion. Источники сайта: src/features/estimate/{catalog.ts,constraints.ts,types.ts,calculations.ts,stageDefinitions.ts}. Числа и допустимые ID принадлежат SPECIFICATION §2–5 и действующему каталогу; здесь не вводится вторая таблица норм.

| Изменение                                                                                         | Влияние на план                                                                                                                                                      | Влияние на стоимость                                                             |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Общая площадь, подтверждённый контур, допустимая этажность (P производный; legacy A/P — по §3.11) | Меняются габариты/доступный объём задачи; прежний план проверяется на актуальность                                                                                   | По существующим формулам калькулятора                                            |
| Количество спален и санузлов                                                                      | Меняется обязательный состав помещений; пользователь согласует изменения уже настроенных комнат                                                                      | В пределах существующих зависимостей калькулятора                                |
| Технология стен                                                                                   | Меняются толщины и геометрические ограничения, а также доступная чистая площадь                                                                                      | Существующие материалы и ставки                                                  |
| Высота                                                                                            | Меняется соответствующий геометрический ввод и ограничения профиля                                                                                                   | По существующим формулам калькулятора                                            |
| Цели комнат, вход, обязательные/мягкие связи                                                      | Меняется запрос PLAN                                                                                                                                                 | Через реально изменившиеся общие параметры либо будущую геометрическую ведомость |
| Регион, доставка, отделка и выбранные этапы                                                       | В текущем профиле комнаты и стены не перемещаются, новый поиск не запускается                                                                                        | Обновляется предварительный расчёт                                               |
| Фундамент и покрытие                                                                              | В текущем профиле это настройки расчёта и совместимости; произвольного изменения комнат от них нет. Будущие конструктивные зависимости вводятся своим контрактом S/R | Существующие формулы и проверки совместимости                                    |

Для первых четырёх строк стоимость пересчитывается по существующим правилам калькулятора. Для целей комнат и пожеланий цена меняется только через действительно изменившиеся общие параметры либо будущую геометрическую ведомость. Для последних двух строк обновляется предварительная стоимость; сохранённые сметы остаются прежними.

Площадь калькулятора — сумма площадей этажей по наружным габаритам. Чистые площади комнат, стены и циркуляция различаются. Например, 120 м² общей площади не означают 120 м² чистых комнат. При передаче не заменять gross на net и не округлять цели скрыто. Периметр вместе с площадью задаёт текущий прямоугольный габарит; для будущих непрямоугольных домов нужен отдельный контракт F14.

Изменение количества комнат не удаляет настроенную комнату, её цель или связи без выбора пользователя. При уменьшении числа спален показать конфликт и предложить выбрать удаляемую/переназначаемую комнату. При увеличении запросить недостающие цели. Предложения по площадям явно обозначаются и подтверждаются, а не выдаются за сведения калькулятора. Несовместимые параметры не исправляются молча.

До T одноэтажный PLAN не принимает floors=2: калькулятор сохраняет свой ввод, интерфейс объясняет ограничение профиля и не превращает два этажа в один. Наличие поля в общем черновике не означает поддержку его значения текущим генератором.

### 3.4. Первое открытие и недостающие сведения

1. Калькулятор переносит известные параметры в свой рабочий черновик. Недостающие обязательные сведения, в том числе контур, состав и вход, уточняются здесь же. Проверенные предложения видны до запуска.
2. «Создать чертёж» фиксирует полный валидный снимок, источник и версии и служит явным запуском одного поиска. sourceEstimateId может отсутствовать. Сохранение расчёта и авторизация для запуска необязательны.
3. PLAN показывает сводку снимка, ход поиска, отмену и результат. При недостающих, устаревших или неподдержанных входных данных вернуть пользователя в тот же контекст калькулятора с причиной. Поиск не запускается.
4. Повтор из PLAN допустим после терминального исхода для того же полного актуального снимка и только по отдельному действию. Изменить параметры можно в калькуляторе.
5. Новый результат показывается для выбора/подтверждения через Controller; предыдущий принятый вариант не заменяется одним фактом окончания поиска.

Для каталога передаются только известные данные. Точный периметр, цели комнат и пригодность иллюстративного плана не выдумываются из площади, фотографии или цены проекта. Предположения существующего диагностического корпуса не становятся пользовательскими фактами.

Если уже открыт более новый рабочий проект, новый внешний снимок не затирает его. Предложить сравнить и применить параметры к текущему проекту либо создать отдельный рабочий проект. Это выбор контекста внутри приложения, а не обязательная новая вкладка браузера. Назад/вперёд восстанавливает представление и фокус, но не накатывает старый URL/snapshot поверх актуального черновика.

### 3.5. Автоматическая связь и явный повторный поиск

Параметры обновляются в текущем черновике автоматически после валидации. **Поиск не запускается на каждое нажатие клавиши.** Стоимость по валидным параметрам может обновляться сразу; размещение комнат меняется по действию «Создать планировку»/«Обновить планировку».

| Состояние                                                       | Поведение                                                                                                                     |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Плана ещё нет                                                   | Заполнить недостающее в калькуляторе, проверить сводку и запустить поиск кнопкой «Создать чертёж»                             |
| План соответствует геометрическому вводу                        | Обычный просмотр; ясно указаны профиль и ограничения                                                                          |
| Геометрический ввод изменён                                     | Сохранить старый вариант с меткой прежних параметров и предложить «Обновить планировку»                                       |
| Поле временно невалидно/не применено                            | Показать ошибку и не маскировать её старой стоимостью как актуальной; старый план остаётся явно прежним                       |
| Идёт поиск                                                      | Показывать стадии/кандидатов и отмену без вымышленного процента; повторный запуск управляется Worker-протоколом               |
| Изменены только настройки цены                                  | Пересчитать текущую предварительную стоимость, сохранив геометрию и её актуальность                                           |
| Поиск отменён/завершился ошибкой или без подходящего результата | Прежний принятый план и сохранённая смета остаются доступны; частичный результат не считается новым принятым проектом         |
| Готов новый вариант                                             | Предпросмотр и явное принятие; старый вариант можно сохранить как предыдущую версию/вариант в пределах существующих лимитов D |

Пример сообщения: «Площадь изменена: 120 → 135 м². Текущая планировка рассчитана для прежних параметров». Не утверждать, что старая геометрия уже соответствует новой площади. Обратный ввод прежнего значения может снять метку устаревания только после проверки нормализованного ввода и версий, а не по совпадению видимой строки.

Для актуальности различать геометрический ввод и настройки цены. Геометрическая сигнатура включает влияющие параметры, комнаты/цели/связи и профиль/версии правил. Она помогает определить устаревание интерфейса, но не заменяет свежую валидацию, принадлежность источника и полноценный контракт Worker.

### 3.6. Ревизии, Worker и устаревшие ответы

В общей оболочке ревизия геометрического ввода и ревизия ценовых настроек независимы. Смена региона не делает уже принятый план геометрически устаревшим. Пока выполняется поиск, ценовой черновик может обновляться без изменения канонической геометрии Project и её baseRevision.

Запуск фиксирует идентификатор контекста, исходный Project/baseRevision, requestId, полный нормализованный геометрический ввод/его ревизию и версии. Результат применяется только к тому контексту и вводу, для которых запрошен. Изменение геометрических полей, в том числе появление невалидного редактирования во время поиска, отменяет/помечает текущую операцию как неприменимую. Запоздалый ответ всё равно отбрасывается по токенам, даже если внешняя отмена не успела остановить Worker.

Совпадение сокращённого hash или одних площади/периметра не разрешает принять ответ другого проекта или переиспользовать сертификат. Project.revision/CAS и requestId/baseRevision сохраняют свои проверки; дополнительная ревизия ввода их не ослабляет. Изменение/сохранение самого Project во время поиска обрабатывается действующим stale-протоколом. Детальный контракт принадлежит ARCHITECTURE и E04.1/E04.3.

### 3.7. Из плана обратно в текущие параметры

Обратный ввод фактической геометрии — действие «Использовать параметры плана в расчёте». Сначала показать diff: текущие и предлагаемые gross area, perimeter, floors и совместимые настройки; цели и чистые площади комнат показаны отдельно.

Подтверждение применяет проверенные значения к общему рабочему черновику и обновляет предварительную стоимость существующим калькулятором. Если текущая геометрия действительно соответствует этим значениям и профилю, проверка актуальности может сохранить её без нового поиска; это не разрешает переносить старый score/proof на изменённый raw без проверки.

Отмена предпросмотра не меняет ни одну сторону. Пока открыт diff, более новая ревизия черновика/Project делает его устаревшим: повторить сравнение, а не перезаписать новые данные старым подтверждением. Неподдержанные/непредставимые настройки объясняются до применения.

#### 3.7.1. Живая правка чертежа, пересчёт черновика и оценка ревизии (CALC-EDIT-2026.11.12-2)

Применение параметров, принятие плана и сохранение сметы остаются отдельными действиями со своими проверками.

| ----------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------- |
| `geometryRevision`      | одна завершённая правка чертежа      | новая геометрия и производные площади комнат                                                 |
| `priceRevision`         | успешный пересчёт текущего черновика | предварительная цена для пары `geometryRevision` и ревизии настроек цены, с версией каталога |
| `scoreRevision`         | завершена проверка оценки            | средний балл именно для этой валидной ревизии                                                |
| `savedEstimateRevision` | явное «Сохранить расчёт»             | сохранённая смета; живые правки её не переписывают                                           |
| `acceptedPlanRevision`  | явное «Принять план»                 | принятый план; правка делает его stale, не заменяет                                          |

**Единица правки.** Одна валидная завершённая операция, которая действительно меняет геометрию, создаёт одну `geometryRevision`. Промежуточный ввод, no-op и повтор той же команды не создают ревизию. Несколько полей применяются атомарно после проверки. Undo/redo восстанавливают значения новой командой без повторного использования ID ревизии. Изменение ручной цели относится к ревизии входа, изменение региона — к ревизии ценовых настроек.

**Порядок после правки:**

1. **Геометрия.** Пересчитать комнаты, их фактические размеры/площади, наружный контур, gross area, perimeter, этажность.
2. **Валидация.** Проверить поддержку профиля, версии, отсутствие пересечений/разрывов и обязательные ограничения. Невалидная правка не даёт новую цену.
3. **Производные поля.** Обновить в текущем черновике только поля, которыми владеет геометрия: A/P, этажность, размеры, фактические площади комнат. Пользовательские настройки цены — регион, доставка, отделка — не трогать.
4. **Цена.** Один раз вызвать существующую функцию предварительной стоимости для нового черновика. Не суммировать дельты вручную, не округлять повторно, не запускать Worker.
5. **Панель.** Под чертежом показать итог, дельту, комнаты, контур, статус кастомного варианта и оценку с её ревизией.
6. **Stale.** Принятый план остаётся, но помечается «рассчитан для прежней ревизии». Автоматической замены плана и автоматической генерации нет.
7. **Оценка.** При наличии полного проверенного набора фактов допускается короткий debounce. Дорогое измерение текущего фиксированного плана запускается отдельно кнопкой «Перепроверить оценку» с отменой и своим бюджетом. Оно не ищет другие планировки.
8. **Сохранение.** Живой пересчёт меняет только черновик. «Сохранить расчёт» записывает проверенный актуальный снимок сметы. Сохранение не выполняет оплату и не меняет ранее оформленный расчёт.

**Защита от циклов.** Поля делятся на:

- `derivedFromGeometry` — только чтение, обновляются из чертежа;
- `userPricingInput` — регион, доставка, отделка, скидки;
- `savedSnapshot` — только явное сохранение.

Геометрия обновляет `derivedFromGeometry`, цена читает их и `userPricingInput`, но никогда не пишет обратно в геометрию. Поэтому цикл «калькулятор → чертёж → калькулятор» невозможен.

**Классификация правок:**

| Что изменено                             | Геометрия/комнаты                                | Текущая цена                                      | Принятый план                                   |
| ---------------------------------------- | ------------------------------------------------ | ------------------------------------------------- | ----------------------------------------------- |
| Внешняя ширина/глубина, площадь, сторона | новые A/P и фактические площади                  | пересчитывается автоматически                     | stale; нужна явная новая генерация              |
| Этажность, технология, чистая высота     | обновляются совместимые поля                     | пересчитывается автоматически                     | stale; нужна явная новая генерация              |
| Внутренние стены/комнаты/проёмы          | новые фактические площади/размеры                | при тех же входах калькулятора цена та же         | после валидации кандидат можно принять напрямую |
| Ручная цель комнаты                      | цель становится `fixed`; факт показывается рядом | цену дома не меняет                               | stale; auto-цели не переписываются              |
| Регион/доставка/отделка                  | не меняется                                      | пересчитывается без Worker                        | не меняется                                     |
| Неподдержанная правка                    | отказ с причиной                                 | остаётся последняя валидная цена с меткой ревизии | сохраняется                                     |

**Панель под чертежом.** На desktop — под холстом; на mobile — под холстом, сворачиваемая, без горизонтального скролла. Обязательные элементы:

- «Итого» и дельта к предыдущей/сохранённой ревизии;
- пометка «предварительно»;
- список комнат: факт, цель, режим auto/fixed, изменение;
- контур, P, gross area;
- бейдж «Кастомный вариант» и список отличий;
- средний балл, `scoreRevision` и статус «проверено / требует перепроверки / недостаточно данных»;
- действия: «Сохранить расчёт», «Перепроверить оценку» (если нужно), «Принять план» (для валидного кандидата).

**Оценка.** E05.5 привязывает существующий итог C15 к ревизии фиксированного плана. Вес, шкалу и формулу задаёт [score-mvp-2026.10.26-1](GENERATION_ALGORITHM.md#c151--контракт-рейтинга-score-mvp-20261026-1). `SCORE-REV-2026.11.12-1` версионирует привязку и показ результата:

- балл считается только по свежей валидной геометрии с полным покрытием применимых критериев C15;
- допустимы только штатные исключения C15. Ошибка, отмена или лимит измерения не превращают критерий в исключённый;
- старый балл нельзя переносить на новую ревизию;
- балл не влияет на цену, принятие и запуск поиска;
- «кастомный» — статус происхождения, не отрицательная оценка.

**Ошибки.** Невалидный preview сохраняет последнюю принятую в черновик геометрию. Ошибка цены при валидной правке сохраняет геометрию и прежнюю цену как историческую, с указанием её ревизии. Запись актуальной сметы требует актуальной цены. Ошибка оценки не блокирует сохранение/принятие. Поздняя цена или оценка применяется только при совпадении контекста, плана, входных ревизий и версий. Undo запускает проверку для восстановленных значений.

### 3.8. Стоимость, сохранение и ошибки

До полноценного R быстрый калькулятор остаётся **предварительным расчётом по параметрам**. Рядом с ценой видно, к какой версии параметров она относится. Чертёж сам по себе не превращает её в геометрическую ведомость. После R точные количества и допущения сметы PLAN привязываются к одному проверенному снимку и версиям; первоначальная смета сохраняется отдельно.

Изменение текущего черновика не переписывает сохранённый estimate/PDF, демонстрационное подтверждение или запись оплаты. Сохранение изменённого расчёта следует существующему явному сценарию новой/обновлённой версии. «Новый расчёт» по-прежнему создаёт стандартный ввод; «Продолжить» открывает выбранную версию и не импортирует случайный старый снимок.

Если новая смета не сохранилась, старая не выдаётся за актуальную и переход к оформлению не подставляет её незаметно. Ошибка сохранения плана сохраняет состояние «не сохранено», а не успешную отметку. Результат по старой геометрии и расчёт по новым параметрам можно просмотреть отдельно с метками; объединённый документ «этот план + эта смета» требует совпадающего снимка и успешной проверки актуальности. Самостоятельный рабочий сценарий калькулятора не блокируется отсутствием необязательного плана.

PLAN остаётся в своей IndexedDB, существующие записи сайта сохраняют свой контракт хранения. Между разными хранилищами не обещается атомарная транзакция. E06 описывает порядок записи, версии связей, идемпотентный повтор и честное частичное состояние: исходные записи не удаляются до успешного подтверждения новой связи. Refresh/back, конфликт двух вкладок и ошибка квоты не превращаются в потерю исходной сметы или молчаливое слияние проектов.

### 3.10. Обязательные адресные сценарии приёмки

1. Калькулятор → план: обязательные поля заполнены в калькуляторе. Один явный запуск передаёт снимок в PLAN и начинает поиск. Повторный клик, back/forward, refresh и remount не повторяют запуск.
2. Каталог → калькулятор → план: сохранены известные настройки; нет выдуманных размеров комнат и скрытой подмены комплектации.
3. Переключение трёх представлений, back/forward и refresh: тот же рабочий контекст, актуальный черновик, выбранный вариант и честный статус сохранения.
4. Изменение площади/подтверждённого контура/технологии (legacy P отдельно): старый план помечен прежним, новый поиск только по действию; после отмены старый вариант доступен.
5. Изменение региона/доставки/отделки: цена обновилась, комнаты не переместились, Worker не стартовал повторно и применимый ответ не отброшен только из-за ценового черновика.
6. Изменение количества спален/санузлов при пользовательских целях: конфликт показан, комнаты/цели/связи не удалены молча.
7. Ошибка числового ввода, невалидное редактирование во время поиска, повторный запуск и late reply: поле объяснено, старый результат не принят как новый.
8. Открытие другого проекта/сметы поверх более нового рабочего черновика: осознанный выбор контекста, исходник сохранён.
9. План → diff → подтверждение/отмена: gross/net различаются; более новая ревизия делает старый diff неприменимым.
10. Ошибка записи сметы/Project, квота и конфликт вкладок: нет ложного save, потери исходника или оформления по старой смете.
11. Floors=2 до T: явное ограничение PLAN, калькуляторный ввод сохранён.
12. Мобильный и планшетный экран: параметры доступны без второй формы, панель не перекрывает основные действия, клавиатурная навигация работает.
13. Результат/PDF/смета относятся к обозначенным снимкам; несовпадение версий видно и блокирует только совместное представление как согласованного документа.
14. Обычные страницы сайта не загружают PLAN целиком; нет второй React, копии формул или неподтверждённого сетевого/ИИ-сервиса.

#### Автозаполнение обязательно

При открытии «Планировки» из текущего калькулятора известные валидные данные подгружаются автоматически: площадь, поддерживаемая этажность, технология, число спален/санузлов, известная высота с согласованным смыслом. Не нужны повторный ввод, отдельная кнопка «Импортировать», сохранение сметы или вход. Дальнейший валидный ввод автоматически синхронизируется между представлениями в том же рабочем контексте; старый снимок не импортируется повторно при переключении вкладки.

Автозаполнение не равно автоматической перестройке/принятию чертежа. Геометрическая правка помечает прежний план устаревшим и обрабатывает активный поиск по действующему протоколу; поиск и принятие нового результата остаются явными. Ценовая правка обновляет предварительную стоимость без регенерации. Сохранённые сметы/планы/документы не переписываются автоматически.

Подтверждение нужно при выборе другого источника поверх текущего проекта, изменении настроенного состава комнат, замене принятой геометрии или записи сохранённой версии, а не для переноса каждой цифры калькулятора. Origin фиксируется при выборе источника, не на каждый ввод; сырой временно невалидный текст отделён от проверенного снимка. Не выдавать старое значение/цену за актуальные, пока текущий ввод невалиден.

#### Полный путь и два режима габаритов

1. **Из калькулятора:** известные данные подгружаются автоматически, недостающее заполняется там же. **Прямой публичный вход:** открывает калькулятор при отсутствии актуального handoff. Автономный стенд сохраняет локальный мастер для разработки и отдельной проверки.
2. **«Знаю площадь»:** площадь — заданная цель. Приложение предлагает допустимые пропорции с изображением контура и длиной/шириной; до выбора неизвестный контур не подтверждён. При сохранении площади изменение одной стороны явно пересчитывает другую, без скрытой смены режима.
3. **«Знаю размеры»:** пользователь задаёт наружные длину/ширину, площадь/P вычисляются. Переключение режима с изменением уже заданной площади показывает последствия до применения. A/длина/ширина/P не редактируются независимо; обязательное ручное поле P в обычном сценарии не требуется. Legacy A/P API автоматически не удаляется.
4. **Помещения:** перенести число спален/санузлов в один список; уточнить кухню-гостиную либо раздельные кухню/гостиную и дополнительные помещения. Площади имеют видимый режим «Автоподбор» либо фиксированный ручной ввод по уточнению ниже. Auto-цели пересчитываются автоматически; предложения изменения fixed-целей принимаются явно. Пустое ручное поле не ноль и не скрытое включение auto.
5. **Вход/пожелания:** понятный вопрос об отдельном входном помещении/тамбуре, без требований знать entrance/derived hall. Пожелания необязательны, доступ проверяется без заполнения полного графа. Техническая комната/второй санузел не добавляются ради success без согласия пользователя.
6. **Сводка/запуск:** цели и подтверждённые размеры, состав/площади комнат, обязательные условия и предупреждения. Предпроверка бюджета не доказывает размещение. Объединение «Подтвердить параметры» и «Далее» должно сохранить явное подтверждение источника/изменений.
7. **Результат:** фактические размеры/площади, отклонения от пожеланий, явное принятие. Диагностику раскрывать отдельно; существенные ограничения строительной/мебельной проверки сохранять читаемыми. Отказ по времени/лимиту/поддерживаемым схемам не доказывает невозможность дома.

Предложения пропорций готовят габариты, не расширяют незаметно семейства/лимиты поиска. Поворот показывать на контуре; 0°/90° без участка/севера не являются солнечной ориентацией. Floors=2 до T объяснять без подмены на1. Террасы/балконы и совпадение с фотографией каталога не обещаются.

#### Числовой контракт до реализации

Сейчас стороны восстанавливаются из A/P; шаг P и ceil-границы заданы SPECIFICATION §2. Контрпример:8×8,25м даёт66м²/P32,5м, но действующий нижний порог33м отклоняет этот корректный прямоугольник. Это продуктовое ограничение прежнего envelope, не разрешение молча ослабить валидатор или подогнать тесты.

Владелец04.11.2026 утвердил U07.2: [SPECIFICATION §2.1](SPECIFICATION.md#21-утверждённый-точный-прямоугольный-ввод--u072) задаёт точность/пропорции/диапазоны/округление, цель и факт; [ARCHITECTURE §3.1](ARCHITECTURE.md#31-точный-габарит-u072-и-границы-u073) — источник/конверсию/версии/Worker. Реализация только в последовательных U07.3a–d, не в этой документационной задаче. Калькуляторные числа и формулы пока не меняются, прежний P без контура остаётся ориентиром. E02/E04 позднее подключают подтверждённую v2-спеку без повторного ввода, сохраняя обязательный калькуляторный вход §3.13. Непредставимый обмен не должен незаметно менять дом: показать причину и вариант явного изменения. Невозможный P, ограничение продукта и ошибка округления — разные причины отказа. Строительные формулы/допуски комнат/отрицательные эталоны этой задачей не меняются; несовместимое числовое решение согласуется до кода.

#### Уточнение владельца: автоматические и фиксированные площади

04.11.2026 владелец выбрал: **«Автоматически менять площади с режимом “Автоподбор”; введённые вручную фиксировать и при конфликте объяснять причину».** Это уточняет прежнее правило явного принятия предложений; не разрешает менять все цели или состав автоматически. Отсутствующие обязательные помещения показывать на шаге списка комнат, как только есть необходимые данные; зависимое от входа проверять при выборе входа.

| Режим                  | Поведение                                                                                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Автоподбор             | Приложение пересчитывает площадь из текущего габарита, состава/ограничений и fixed-целей при изменении этих данных; режим и перечень изменённых площадей видны |
| Фиксированная площадь  | Ручное пожелание сохраняется; автоуменьшение/увеличение запрещено. Допуск геометрии SPECIFICATION §3 действует, fixed не означает нулевой допуск               |
| Конфликт после подбора | Сохранить ввод, объяснить конкретные ограничения, предложить явно освободить/изменить цели либо габарит/состав. Не нарушать минимум и не увеличивать дом молча |

Новая комната может начинать с видимым «Автоподбором». Ручное редактирование фиксирует площадь, промежуточный/невалидный текст не перезаписывается распределителем. «Вернуть автоподбор» — явное действие. Пустое ручное поле не равно нулю и не включает auto скрыто. Старые числовые цели без режима считать fixed; совпадение с минимумом не доказывает согласие на auto. Импорт/сохранение режимов — в соответствующих D/E-контрактах.

Автоматика меняет только площади auto-комнат. Количество/типы комнат, двери/связи, fixed-цели, наружная площадь и технология не изменяются ради success. Новая общая площадь из калькулятора переносится автоматически; старый контур/цели не подменяют её, а конфликт остаётся видимым до решения по режиму габаритов. Добавление недостающего санузла требует действия пользователя, после него auto-цели могут перераспределяться. Предложения изменения fixed/состава остаются preview до согласия.

Числовая политика U07.4a и ручные эталоны закреплены в [SPECIFICATION §4.1](SPECIFICATION.md#41-автоподбор-целей-до-построения-плана). До геометрии доступны минимальные цели профиля и проверка нижней оценки. Раздача остатка ждёт отдельного контракта с подтверждённым чистым бюджетом. Предпроверка целей не гарантирует размещение, проходы и мебель.

Пересчёт строится из одного актуального снимка, не из повторно округлённого результата. Ввод/производные auto-цели меняются согласованно без циклов калькулятор→округление→новый перенос. Значимая геометрическая правка сохраняет invalidate/revision/cancel/stale, принятый план не заменяется, Worker не стартует на ререндер. До→после для auto-целей видно; режимы и ручной ввод сохраняются при возврате по шагам.

Проверки U07.4/U07.5:66м² со смешанными auto/fixed; уменьшение/увеличение габарита; fixed+минимумы auto не помещаются; все цели fixed; auto→ручной→auto; пустой/невалидный ввод; смена типа/добавление санузла/удаление комнаты; одинаковый пересчёт/обмен без дрейфа; устаревший результат после смены режима; цели/факт/допуск различаются. Успех распределения бюджета не success геометрического поиска.

#### Санузел и канализация — разные настройки

Назначение помещения (туалет, ванная/душевая, совмещённый санузел) отличается от инженерной системы дома. Сейчас RULES содержит один bathroom-профиль с предполагаемыми toilet/basin/shower; реальная расстановка/проходы — R01–R02. Отдельные туалет/ванная или ванна вместо душа не становятся поддержанными типами переименованием. Для разделения нужен отдельный версионированный контракт оборудования, размеров, подсчёта санитарных функций и совместимости калькулятора; два одинаковых bathroom не подменяют раздельные функции.

Септик — часть автономной системы канализации/очистки стоков дома и участка, не «технология комнаты». Сейчас он не выбирается и не рассчитывается; строка калькулятора «разводка канализации» не цена/проект септика. R12/R13.3 предусматривают точки/демо-объёмы, не внешнюю систему и её размещение. Новый обязательный вопрос о септике для текущей анкеты не требуется.

В будущем инженерном разделе допустимы намерения «центральная канализация / автономная / пока не определено». Конкретная автономная технология выбирается по данным участка/использования и инженерной проверке, не по одному числу санузлов, площади или стеновому материалу. Не назначать объём/место/дистанции без отдельного контракта. Общая справочная основа — [EPA: принцип системы](https://www.epa.gov/septic/how-septic-systems-work) и [факторы/типы](https://www.epa.gov/septic/types-septic-systems); это не локальные нормы проектирования и не новые правила ядра. Инженерное развитие остаётся поздним без расширения U/MVP.

#### Стартовый состав вместо ручного добавления обязательных помещений

Первое открытие нового контекста создаёт **видимое редактируемое предложение**, не готовый проект. Достоверный сохранённый состав/цели важнее шаблона. Состав виден до поиска и редактируется; запуск подтверждает показанное намерение, не строительную пригодность.

Вопрос «Нужен отдельный тамбур?» управляет входным профилем. При тамбуре включить entrance в предложение с auto-площадью; через холл отдельный пользовательский entrance не навязывать. Явное увеличение спален2→3 может добавить одну видимую предложенную auto-строку без второй кнопки импорта, сохранив ID/цели/связи остальных. Удалённая пользователем обязательная комната не воскресает автоматически: ошибка/«Восстановить» на этом же шаге. Распределитель площадей не управляет количеством/типами комнат.

#### Порядок инициализации и пересчёта U07.4a

1. **Источник и состав.** При повторном входе сначала открыть существующий черновик того же рабочего контекста. Для нового контекста использовать достоверный список с его UUID, именами, целями и связями, если он есть. Считать спальни и санузлы из списка. Если достоверный список и известные числа калькулятора расходятся, показать оба значения и запросить решение без создания дублей. При отсутствии списка перенести валидные числа из актуального калькуляторного снимка в E. В автономном мастере пользователь выбирает недостающие числа или принимает видимое предложение по действующему профилю. Отсутствующее число остаётся неизвестным до выбора, несовместимое показывает фактическое значение и допустимые пределы.
2. **Один стартовый шаблон.** Ключ — ID рабочего контекста и этажа плюс идентичность явно выбранного источника. Версии правил и исходного снимка хранятся как происхождение. Обновление данных того же источника меняет вход предпроверки и выявляет расхождения, не инициализирует список заново. При первом предложении из чисел показать спальни, санузлы и кухню-гостиную по умолчанию. Известная пара кухни и гостиной используется как есть. Отдельный вход добавляет предложение тамбура после выбора пользователя. Вход через холл использует производную циркуляцию. Существующая строка тамбура и её связи сохраняются до явного удаления. Мастер не создаёт строки коридоров по шаблону.
3. **Идентичность и поля.** В UI хранить UUID, происхождение строки, режим имени `auto/custom`, режим цели `auto/fixed` и ручной текст. Новые предложенные строки получают auto-имена и auto-цели. Автоимя следует типу и различает однотипные комнаты порядковым номером. Ручное имя сохраняется при смене типа, очистка включает автоимя. Старые непустые имена сохраняются как пользовательские, старые числовые цели без режима — как fixed. Ручная правка цели сразу переключает её в fixed. Пустой или неверный текст остаётся в поле и блокирует числовой пересчёт. Вернуть auto можно отдельным явным действием. `Project` и Worker получают прежние требования с разрешёнными именами и числовыми целями.
4. **Структурные правки.** При выборе 2→3 добавить одну видимую auto-строку, оставив прежние UUID и связи. При уменьшении дать выбрать удаляемую комнату и показать затронутые связи. Удалённая обязательная комната даёт адресную причину и предложение восстановления. При разделении общей зоны показать, какой UUID сохраняется, какие связи требуют переназначения и какие цели получатся. Например, fixed 20 м² можно явно разнести на кухню 6 и гостиную 14 м², если предложение проходит доступную предпроверку. Другой явный выбор — включить auto для обеих. Для обратного объединения показать итоговую цель и судьбу обеих исходных связей. Отмена оставляет исходный список. При получении пожелания о раздельном санузле, ванне вместо душа или отдельном гостевом WC сообщить о границе текущего профиля.
5. **Один пересчёт на правку.** Подготовить текущие числовые цели по SPECIFICATION §4.1 и проверить их вместе. Не использовать прошлые округлённые auto-цели как вход. При пустом/невалидном fixed, неподтверждённом габарите, неподдержанной версии или доказанном превышении нижней оценки сохранить ручной текст и не применять частичный набор auto. Предыдущий рассчитанный набор при показе пометить устаревшим. При отсутствии auto проверить ручной набор без его изменений. При успешном пересчёте показать только изменившиеся auto-цели с прежними и новыми значениями. Числовой результат может быть готов до выбора входа. Доступные на шаге диагностики состава и связей остаются отдельными причинами и не исчезают от успешного расчёта площади.
6. **Применение и ревизия.** При явной смене состава, источника или fixed-цели preview содержит контекст, ревизию, UUID, затронутые цели и связи. При применении сверить актуальность и заново выполнить доступную предпроверку. Устаревшее, отменённое или повторное применение не добавляет строки. Значимая правка и её производные auto-цели применяются одной операцией ввода. Действующий invalidate/cancel помечает принятый план устаревшим и сохраняет его. Повтор того же расчёта, возврат по шагам и ререндер не меняют ревизию и не запускают Worker.

В сводке разнести причины по стадии. Для неизвестного/невалидного поля указать, где исправить. Для состава показать недостающую функцию или фактическое число и предел. Для площади при доказанном конфликте показать нижнюю оценку и наружную площадь. Для входа и связей назвать несовместимое условие или конкретную пару. Предложение показывать с исходным и новым значением только после доступной предпроверки на копии ввода. Если подходящей правки нет, сообщить, что нужно уточнить. Отказ Worker по времени, шагам или внутренней ошибке не приписывается отдельной комнате.

#### Раздельный санузел: помещения, функции и приборы

Геометрически проверенный компромисс можно принять явным действием. Для сокращения холла показать, какие комнаты можно увеличить и на сколько или какое дополнительное помещение помещается. Ручные цели требуют подтверждения изменения.
- **Расположение.** Для двух санузлов можно явно выбрать «ближе ко входу» и «ближе к спальням». Проверка кандидата использует путь между порогами по реальным проходам. Для гостевого учитывать длину от входа и предпочтение маршрута через общие проходы без транзита через кухню-гостиную. Для семейного учитывать длину и удобство путей от спален. Соседство двух санузлов допустимо, когда оба выполняют выбранные роли.
- **Проходы и двери.** В текущем профиле 1000 мм чистой ширины маршрута внутри холла или коридора. Отдельно проверяются размеры проёма. Для непрямоугольной зоны оцениваются рабочие проходы и длины маршрутов. Направление створки выбирается по профилю помещения и проверяется с оборудованием, коллизиями и свободным проходом. Для новых санитарных комплектов действуют R01/R02, где учитываются расстановка приборов и задание на проектирование.
- **Приёмка.** Для 120 м² сравнивать площадь проходов и оба маршрута на одинаковом контуре. Проверить ещё случай, когда предпочитаемый вход или размер помещения делает компактный вариант недостижимым в поддержанных семействах. Тогда объяснять компромисс и показывать явно применяемые предложения. Изменение формулы или набора метрик рейтинга проходит отдельный версионированный контракт C15.

До Q01.2 при сумме целей 89 м² автоматический поиск строил холл 14,05 м² и прямую дверь из тамбура в гостевой санузел. Второй санузел был доступен из кухни-гостиной. Для другого набора целей подготовлена ручная схема с холлом 10,40 м². В ней гостевой доступен из тамбура, второй из холла. Двери и оба маршрута прошли проверку. При сравнении результатов сохранять точный баланс площадей, выбранные роли и проверенные маршруты.

В локальном Q01.2 при тех же 89 м² целей и том же бюджете найден холл 14,31 м² с дверью гостевого санузла из тамбура и семейного из холла. При 92,9 м² целей автоматический контрольный проход дал 10,99 м² и те же типы доступа. Эвристика v2 переставляет порядок структур холла при явной положительной связи входа с санузлом и сохраняет все структуры. Общее ранжирование и санитарные профили идут отдельными этапами.

Расположение санузла и состав санитарного комплекта задаются отдельно. Гостевым может быть полный совмещённый санузел или отдельный WC. Для частного дома состав и зонирование задаются в проектном задании, а п. 4.5 различает ванную/душевую, туалет и совмещённый санузел. [СП 55.13330.2016, пп. 4.2 и 4.5](https://nav.tn.ru/cloud/iblock/aa9/aa9f469fbb5bec67426dff50f7250b0d/SP-55.13330.2016-Doma-zhilye-odnokvartirnye.pdf)

В расширенном составе можно совместить полный комплект с дополнительным WC. Для передачи между калькулятором и PLAN использовать утверждённый список комплектов со ссылками на физические помещения. Инвентарь приборов следует из функций, двери берутся из валидной геометрии. Старое поле `bathrooms` представляет только прежние совмещённые комплекты с душем. При разделении фиксированные площади и назначения связей подтверждаются вместе. [Модель и совместимость в R01.1](tasks/R_EDITOR_ESTIMATE.md#модель-совместимость-и-критерии-геометрии)

## 4. Упаковка и данные

Один источник core/UI, без второй React и копий расходящихся исходников. Lazy загрузка не увеличивает обычные страницы всем CAD-кодом. На этапе E ресурсы/Worker/font/cache учитывают import.meta.env.BASE_URL и /osnova/. Прямые адреса проверяются фактически; архивные /plan-маршруты пока не существуют.

PLAN — отдельная IndexedDB osnova-plan-db. Ключи saved estimates, session draft, профиль/оплата сайта не меняются ради PLAN; чертежи не уходят в Supabase. SW scope раннего стенда не перехватывает сайт, после E проверяется взаимодействие кэшей/обновления. Смета/PDF используют один snapshot и версию каталога; ошибка новой сметы не показывает старую как актуальную.

## 5. Документационный push текущей задачи

Действующий CI сайта запускается на push в main и автоматически связывает проверки с Pages. Чтобы выполнить текущий документационный push без сборки/публикации сайта и без изменения CI, commit содержит [skip ci]. Это документированное [правило GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs) для push/pull_request. Локальные проверки документации при этом обязательны. Исключение относится только к текущей документационной задаче; кодовые проверки не отключать, будущие защищённые PR могут требовать обязательные checks. Вручную workflows не запускаются и не перезапускаются.
