# OSNOVA PLAN — независимая валидация и испытания

## 1. Правила задачи

До кода кратко записать в локальном PROGRESS: контракт, положительные/отказные случаи, независимые ожидания и проверки. Не повторять полный файл спецификации. Менять валидатор или его эталоны ради генератора запрещено. Подтверждённая ошибка валидатора исправляется отдельной задачей с контрпримером и прежними обязательными проверками.

Validation проверяет структуру/ссылки/версии, поверхности стен/union, наружные границы, площади/баланс, минимумы/пропорции, проёмы/дуги, настоящий доступ, а на T/R — лестницу/мебель/зоны. Он не мутирует проект и не импортирует генератор. Общий низкоуровневый geometry проверяется независимо. Любой публичный success, импорт и PDF проходят полный набор правил своего профиля. «Не реализовано» не считается успешной проверкой.

## 2. Независимые ожидания

- Бумажные значения: 4000×4000 мм = 16 м²; допуск цели 12: 12,25 допустимо, 12,26 нет; цели 16: 16,32 допустимо, 16,33 нет. Отдельно минимумы: допустимое отклонение не разрешает комнате стать меньше минимума.
- Дом 10000×8000, наружная стена 300: внутри 9400×7400 = 69,56 м². Комнаты 4200×7400 = 31,08 и 5100×7400 = 37,74, перегородка 100×7400 = 0,74. Вместе 69,56; наружный след 10,44 и полный баланс 80. Это аналитический тест геометрии, не готовый жилой план.
- A=96, P=40 → 12×8 м. Две полосы 1000×100 с квадратом пересечения 100×100 → union 190000 мм².
- Ось 4000 мм и толщина 125 мм → поверхности 3937,5/4062,5: проверяет doubled-mm независимо от нынешних чётных толщин.
- Второй exact oracle для малых прямоугольных сцен: разбить плоскость по всем X/Y границам на непересекающиеся клетки, независимо классифицировать их по исходным прямоугольникам и суммировать BigInt-площади. Не вызывать production union/ledger. Проверить граничные/полумиллиметровые случаи.
- Растр 10 мм годится только дополнительным oracle для строго выровненных по этой сетке тестов. Он не доказывает равенство произвольных площадей или отсутствие щели 1 мм.

## 3. Корпуса и пригодность поиска

Корпус создаётся до проверяемого поиска. provenFeasible — ручной witness, независимо пересчитанные размеры/связи и проверка полного текущего профиля; expectedFeasible — гипотеза; invalidInput — доказанно неверный ввод. noSupportedLayout не доказывает геометрическую невозможность.

MVP использует первые 10 простых одноэтажных witness. Ещё 10 сложных одноэтажных и 10 двухэтажных доводят корпус полной v1 до 30; после мебели все необходимые witness обогащаются ею до финального гейта. Эталон не создаётся тестируемым генератором. Пороги — только [ACCEPTANCE.md](ACCEPTANCE.md).

C07–C08 закрепляют эти десять входов и ручные решения до кода поиска. В корпусе должны различаться площадь/пропорции дома, состав/число комнат, цели и связи, технологии/толщины и положение входа. Повороты одного плана не заменяют разнообразие. Для каждой из трёх схем нужен хотя бы один ручной пример; случаи могут иметь решения в нескольких схемах. Не менее трёх входов имеют ручное решение для центрального холла: их ID составляют N_hall, окончательная принадлежность контракту фиксируется в C09.1 до C09.2. Для каждого witness хранить исходные требования, координаты/размеры/двери/окна, независимый расчёт площадей/зазоров/связей и основание feasible; не только готовый golden проверяемого валидатора.

Дополнительно подготовить не менее трёх диагностических входов с ручными witness иной организации комнат, чтобы исследовать границы трёх схем. Это отдельный набор, не часть знаменателя K2. Форма исходного witness сама по себе не доказывает, что тот же ввод не имеет другого решения в поддерживаемой схеме. Явно различать «поддержка не установлена» и обоснованное отсутствие в конкретном семействе; noSupportedLayout не является доказательством невозможности дома. Успехи и причины отказа этого набора считать отдельно.

После независимого пересчёта каждый witness реально просмотреть как SVG с размерами, назначениями, дверями/дугами и окнами; в локальном PROGRESS записать ID/версию корпуса, путь к изображению и замечания. B12 сейчас показывает фиксированный геометрический план и не доказывает готовность такого просмотра полного witness: в C07 до приёмки первого корпуса предусмотреть минимальный диагностический read-only вывод, при необходимости отдельной подзадачей. Визуальный просмотр Codex, подтверждение владельца и математическая проверка — отдельные свидетельства; отсутствие ответа владельца записывать pending, не придумывать приёмку. Проверка картинки не заменяет арифметику, независимый код не означает независимого автора.

Корпус фиксируется ID/версией и контрольной суммой до поиска; входы и ожидания не переделывать после неуспешного прогона. Подтверждённая ошибка witness исправляется отдельной задачей с контрпримером и записью причины. Поиск вправе найти любую валидную планировку исходных требований, он не обязан повторять геометрию witness.

Каталог — дополнительный реалистичный набор: src/features/projects/catalog.ts и floorPlans.ts, иллюстрации public/images/floor-plans. На 20.10.2026 одноэтажные ID 01/03/04/06/08, двухэтажные 02/05/07. Площадь/число спален не доказывают выполнимость набора целевых чистых площадей. У каталога нет точного периметра: аспект 3:2 допустим только как явно подписанное предположение теста с проверкой границ калькулятора; это не глобальное правило rules.ts. SVG-картинка не является точной канонической моделью. Пока нет проверенного witness, «4 из 5 домов» не жёсткий критерий приёмки.

## 4. Повреждения, свойства и случайные прогоны

Перед публичным generate — минимум 12 независимых mutation-классов: выход за контур, overlap, ошибочная толщина, разрыв, площадь, минимум стороны, ложное соседство углом, удалённая дверь, дверь вне стены, наложенные проёмы, отсутствующее обязательное окно, нарушенная приватность. Позже добавить мебель, лестницу/void, ссылки/версии и stale-результат. Для каждой мутации заранее указать ожидаемый issue; не любое смещение на 1/50 мм ошибочно само по себе.

Свойства: frozen input не мутирует; exact balance; отсутствие запрещённых пересечений; rotation/mirror сохраняют площади и связи с переназначением сторон/дверей; сериализация roundtrip; одинаковый processed prefix воспроизводится; намеренная подмена внутреннего шага плохим кандидатом не достигает success. Отключённый валидатор должен быть обнаружен тестом.

В каждой маленькой задаче — связанные unit/contract и границы. 500 property-примеров нужны при изменении соответствующей геометрической операции; до C11 они не требуют отсутствующего generate. C11.2 запускает закреплённую десятку с отдельным итогом N_hall и диагностического набора по раннему критерию ACCEPTANCE; это не полный K2. Далее — адресные регрессии; на C16 и последующих поисковых контрольных точках — 2000 seeded смешанных входов плюс отдельный provenFeasible корпус. Повторный полный случайный прогон нужен при изменении поиска/правил, а не при CSS/PDF/журнале. Проверять и отклонённые случаи классификацией: «все отклонены» не является качественным генератором.

Лог: версии/seed/профиль/шаги/время/число случаев, успехи и отказы по статусам, coverage технологий/границ, найденные counterexamples и три показательных отказа. Успех на provenFeasible измеряется отдельно от mixed random; golden сохраняется после независимой проверки, изменение требует объяснения. Эталонные входы не меняются ради процента.

## 5. Команды и браузеры

Существующие команды отдельного проекта: pnpm run typecheck:core, pnpm run typecheck, pnpm run lint, pnpm test -- tests/unit/<file>.test.ts, pnpm run test:e2e -- <file>.spec.ts, pnpm run build, pnpm run format:check, pnpm run backup. Плейсхолдеры путей заменять существующим тестом. Script check отсутствует; backup реализован в B13 через scripts/backup.mjs. При прямом запуске Vitest использовать `node node_modules/vitest/vitest.mjs run <файлы>`: не добавлять лишний `--`, который в прежнем запуске расширил выборку. Проверять package.json перед запуском; полный синтаксис backup — локальный README.

TypeScript — для логики/интерфейса; ESLint — изменённые TS/TSX по CLI существующего eslint; целевые Vitest — логика; браузер — затронутый сценарий. Браузерный preview B01 требует актуальной сборки именно генератора. Полные проверки генератора выполняются на гейтах, сайт — только E. Успешные проверки не повторяются ради отчёта.

Desktop/mobile viewports, Chromium/Firefox/WebKit и реальный Safari различаются. Скриншоты реально просматривать; viewport не доказывает iPhone. Реальные результаты предоставляет владелец, до ответа статус pending. Доказательства записываются в локальный PROGRESS, публикационные результаты — с версией/URL и согласием владельца.
