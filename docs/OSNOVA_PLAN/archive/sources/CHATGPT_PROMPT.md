# CODEX — OSNOVA PLAN v3.0

## Полная переработка документации, дорожной карты и правил разработки

### 1. Контекст проекта

Мы разрабатываем **OSNOVA PLAN** — самостоятельный браузерный генератор концептуальных чертежей и планировок частных домов.

В дальнейшем приложение будет интегрировано в основной сайт строительной платформы OSNOVA.

OSNOVA является демонстрационным портфолио-проектом, а не действующей строительной компанией. Однако генератор должен быть технически качественным, полнофункциональным в пределах заявленных возможностей и пригодным для демонстрации потенциальным заказчикам.

Основные функции:

- Ввод параметров дома.
- Выбор технологии строительства.
- Определение этажности.
- Выбор помещений и их целевых площадей.
- Алгоритмическая генерация планировки без генеративного ИИ.
- Проверка геометрической корректности.
- Визуализация чертежей.
- Сохранение и повторное открытие проектов.
- Экспорт PDF на устройство пользователя.
- Последующее расширение до CAD-подобного редактора.
- Интеграция с основным сайтом OSNOVA.

Разработка выполняется непосредственно в реальных файлах проекта и подключённом GitHub-репозитории.

### 2. Главная задача

Сейчас существуют две версии документации.

**Версия 1 — Codex.**

Находится в исходном проекте OSNOVA PLAN и включает техническую спецификацию, архитектуру, математическую модель, дорожную карту, тестирование и требования к будущей интеграции.

**Версия 2 — Claude.**

Отдельный файл `GENERATOR PLAN.md`, содержащий альтернативную дорожную карту, более строгие правила независимого тестирования и поэтапное создание MVP.

Твоя задача — создать **третью единую версию документации OSNOVA PLAN v3.0**, которая будет использоваться как основной источник требований для всей дальнейшей разработки.

Не объединяй документы механически.

Необходимо:

1. Прочитать обе версии полностью.

3. Проверить фактическое состояние существующего проекта.
4. Определить сильные и слабые стороны каждого варианта.
5. Выявить технические противоречия.
6. Принять согласованные архитектурные решения.
7. Сохранить обязательные требования, необходимые для дальнейшего развития.

Результатом должна стать полноценная система документов, по которой можно последовательно разрабатывать генератор без постоянного пересмотра фундаментальных решений.

### 4. Методика работы Codex

Возьми из документации Claude лучшие принципы организации разработки.

**Одна задача — один запрос.**

Каждая задача должна быть небольшой, однозначной и проверяемой.

Для каждой задачи определяй:

- Что необходимо реализовать.
- Какие файлы использовать.
- Какие тесты написать.
- Какие проверки выполнить.
- Какие результаты должны получиться.
- Что требуется проверить вручную.

После задачи обязательно выполняй предусмотренные проверки.

Если проверки не пройдены, не переходи к следующей задаче.

Не допускай подгонки тестов под ошибочную реализацию.

Не заменяй полноценную функциональность заглушками, имитирующими успех.

Фиксируй фактически выполненные задачи, ошибки, результаты проверок и нерешённые проблемы в `PROGRESS.md`.

При реализации генератора используй независимые эталоны, случайные тесты, граничные значения и повторяемые seed.

В дальнейшем работай с небольшими самостоятельными задачами, чтобы уменьшить риск ошибок и чрезмерного расходования контекста.

### 5. Требования к генератору

Генератор должен учитывать:

- Площадь и геометрические размеры дома.
- Периметр, если он используется во входных параметрах.
- Строительную технологию.
- Наружные стены и внутренние перегородки.
- Целевые площади помещений.
- Минимальные допустимые размеры комнат.
- Пропорции помещений.
- Коридоры и холлы.
- Расположение входа.
- Двери и окна.
- Доступность каждого помещения.
- Этажность и лестницы.
- Допустимые отклонения.
- Функциональность и качество планировки.

Обязательно раздели:

**Геометрическую корректность** — план соответствует математическим и техническим ограничениям.

**Функциональное качество** — помещения логично расположены, проходы удобны, коридоры не занимают чрезмерную площадь, отсутствуют бессмысленные конфигурации.

Корректная арифметика сама по себе не означает хорошую планировку.

Опиши систему оценки вариантов и выбора лучшего найденного результата.

Не обещай успешную генерацию для любых входных данных.

Предусмотри честные статусы отказов, отмены, ограничений алгоритма и внутренних ошибок.

### 6. Независимая проверка

Объедини лучшие решения по тестированию из обеих документаций.

Валидатор должен проверять:

- Границы здания.
- Площади помещений.
- Толщины стен.
- Отсутствие недопустимых пересечений.
- Геометрический баланс.
- Минимальные размеры.
- Дверные и оконные проёмы.
- Достижимость помещений.
- Межэтажные соединения.
- Остальные обязательные инварианты спецификации.

Валидатор должен оставаться логически независимым от генератора.

Задачи генератора не должны изменять валидатор ради прохождения тестов.

Изменение правил проверки допускается только отдельной документированной задачей.

Предусмотри:

1. Unit-тесты.
2. Эталонные планировки.
3. Намеренное повреждение корректных планов.
4. Property-based тестирование.
5. Случайные прогоны.
6. Проверку повторяемости.
7. Проверки граничных случаев.
8. Регрессионные тесты.
9. Браузерные тесты.
10. Визуальную приёмку.

Используй планы каталога OSNOVA в качестве одного из контрольных наборов.

Для тестовых входов различай доказанную выполнимость, предполагаемую выполнимость и заведомую некорректность.

Не считай надёжность высокой, если алгоритм отклоняет большинство корректных запросов.

Отдельно измеряй долю успешных генераций на заведомо выполнимых примерах.

### 7. Новая последовательность разработки

Необходимо ускорить получение первой работоспособной версии приложения, не жертвуя архитектурой.

Предварительная последовательность:

**Этап 1. Геометрический фундамент**

Типы данных, правила, координаты, площади, стены, топология и независимый валидатор.

**Этап 2. Одноэтажный генератор**

Алгоритмы размещения комнат, схемы планировок, коридоры, двери, окна, оценка вариантов.

**Этап 3. Проверка генерации**

Тестовый корпус, случайные прогоны, граничные случаи, повторяемость, анализ ошибок.

**Этап 4. Рабочий MVP**

Пользовательская анкета, SVG-просмотр, генерация, сохранение, импорт/экспорт при необходимости и PDF.

**Этап 5. Расширение**

Двухэтажные дома, лестницы, сложные связи помещений, дополнительные ограничения.

**Этап 6. CAD-возможности**

Редактирование, история изменений, мебель, смета и расширенные функции.

**Этап 7. Стабилизация**

Производительность, адаптивность, браузерные тесты, офлайн-возможности в пределах спецификации.

**Этап 8. Интеграция с OSNOVA**

Подключение генератора к основному сайту, передача исходных параметров и результатов.

Проверь последовательность зависимостей и скорректируй этапы при необходимости.

Не переноси критические архитектурные компоненты на поздние этапы ради упрощения MVP.

Каждый этап должен заканчиваться измеримой контрольной точкой.

### 11. Полномочия на работу с GitHub

**Ты имеешь моё предварительное разрешение самостоятельно вносить все необходимые изменения документации в рабочий репозиторий OSNOVA PLAN и отправлять их на GitHub.**

Для данной задачи разрешено:

- Создавать файлы документации.
- Изменять существующие документы.
- Переименовывать документы.
- Перемещать устаревшие документы в архив.
- Обновлять `AGENTS.md`.
- Обновлять дорожную карту.
- Создавать и обновлять журнал прогресса.
- Выполнять Git-команды для сохранения изменений.

После завершения изменений ты **обязан выполнить полный цикл**:

1. `git status` — убедиться, что работаешь в нужном репозитории.
2. `git add` — добавить только файлы текущей задачи.
3. `git commit` — создать коммит с понятным названием.
4. `git push` — отправить коммит в соответствующую удалённую ветку.
5. Проверить успешность отправки и синхронизацию с удалённым репозиторием.

**Не останавливайся после `git commit`.**

Git commit не означает, что изменения появились на GitHub.

Задача считается полностью завершённой только после успешного Git push, если удалённый репозиторий доступен.

Если среда требует дополнительного системного разрешения для выполнения push, запроси его.

Если отправить изменения невозможно, прямо сообщи причину, не выдавая локальный коммит за опубликованную работу.

Запрещено:

- Выполнять `git push --force`.
- Переписывать историю Git.
- Удалять чужие изменения.
- Менять посторонние репозитории.
- Вносить изменения в основной сайт OSNOVA.
- Использовать другой remote без обоснования.
- Публиковать основной сайт без отдельного поручения.

При дальнейшей разработке в рамках утверждённой дорожной карты эти правила Git также действуют, если не установлены более строгие ограничения для конкретного этапа.
