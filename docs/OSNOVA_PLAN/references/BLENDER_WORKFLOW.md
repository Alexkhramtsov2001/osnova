# Blender и MCP — будущая локальная процедура

Согласовано с владельцем 23.10.2026 после обсуждения документа Claude «Промты Codex + Blender MCP (этап 2D 3D)». Ниже сохранена процедура подключения с уточнениями для OSNOVA PLAN; исходный DOCX не требуется для её исполнения. Это будущая инструкция, не поручение устанавливать или запускать Blender сейчас.

Владелец сообщил, что Blender уже скачан. Установка, версия, путь, расширение и MCP ещё не проверены; скачивание не считается успешной настройкой.

## Роль и момент подключения

- Геометрическое ядро, размеры, площади, ограничения, 2D-редактор, SVG и векторный PDF не зависят от Blender/MCP. Числа и допуски остаются у [SPECIFICATION](../SPECIFICATION.md), канон — у [ARCHITECTURE](../ARCHITECTURE.md).
- Будущий интерактивный 3D строится локально в браузере из того же подтверждённого документа проекта. Посетителю не нужны Blender, MCP, ИИ, ключи или собственный сервер. Рабочий Blender разработчика не обслуживает запросы посетителей сайта.
- Blender — дополнительный инструмент разработчика: мебель и другие повторно используемые модели, материалы, проверка сцен, экспорт и презентационные рендеры. Фотореализм не является обязательной приёмкой G01–G04.
- MCP помогает исследовать сцену и отлаживать операции. Повторяемые преобразования закрепляются в сохранённых проверяемых Python-сценариях; новые текстовые запросы к модели не становятся алгоритмом построения каждого дома.
- При выполнении [G01](../tasks/GH_FUTURE.md#g01--контракт-2d--3d), после его существующих зависимостей, определить конкретную потребность в Blender и контракт обмена. Если она есть, выполнить процедуру ниже отдельными малыми шагами перед зависимой работой G02–G04. Если браузерному 3D он не нужен, настройка не блокирует эти карточки; вернуться к ней при первой задаче с моделями/материалами/рендером Blender.
- Владелец поручил выполнить эту процедуру, когда возникнет такая задача; повторно спрашивать, нужен ли сам согласованный подход, не требуется. Это не разрешает ранний запуск, публикацию исходников генератора, изменение сайта или выполнение следующих карточек без поручения. Нужные действия в интерфейсе и недостающие права уточняются на фактическом шаге.

## Контракт геометрии до подключения

1. Вход — подтверждённая ревизия документа генератора: ID, контуры, стены, толщины, этажи, отметки, высоты, проёмы и поддержанные наружные площадки. Blender не придумывает недостающие размеры и не исправляет планировку самостоятельно.
2. Явно задать оси, начало координат и преобразование миллиметров в метры и обратно для проверок. Преобразование выполняется в одном адаптере; допуски ядра не ослабляются ради вида.
3. Объекты сцены сохраняют связь с исходными ID/revision. Изменённый проект требует нового производного результата; устаревшая сцена не считается текущей. Обратный импорт правок из Blender — отдельный будущий контракт, не скрытое изменение канона.
4. GLB и `.blend` — производные файлы, не замена документу проекта, правилам помещений или пользовательским сохранениям. Статический GLB подготовленного объекта не подменяет построение произвольного пользовательского дома в браузере.
5. Для ассетов задать бюджет полигонов, текстур и размера загрузки под мобильные устройства; проверять поддержанные материалы в целевом браузере. Сжатие включать только при наличии совместимого декодера, с проверкой локальной/офлайн-загрузки. Новые зависимости и точные бюджеты определяются контрактом соответствующей карточки, не этой инструкцией.

## Шаг 1 — окружение и MCP-сервер

- Работать локально в Windows/PowerShell, отдельно от сайта и генератора. Не вводить WSL/Docker/виртуальную машину как обязательную зависимость. Не менять системные настройки безопасности ради установки.
- Сначала проверить уже скачанный Blender: установлен ли он, фактические версия и путь. На дату обсуждения официальная страница MCP указывает Blender 5.1 или новее; перед настройкой заново проверить совместимость. Номера MCP, порт и команды из старого промпта не считать закреплёнными.
- Использовать официальные [страницу Blender MCP](https://www.blender.org/lab/mcp-server/), [Setup](https://projects.blender.org/lab/blender_mcp/wiki/Setup) и репозиторий `https://projects.blender.org/lab/blender_mcp.git`. Не подменять его одноимённым сторонним пакетом `blender-mcp` из PyPI или командой `uvx blender-mcp`.
- Рабочая папка — `blender_mcp` в реальном профиле пользователя, определённом через `[Environment]::GetFolderPath('UserProfile')`; не переопределять `$HOME`. Если папка уже есть, сначала проверить origin, commit и локальные изменения. Не применять reset/clean или `safe.directory=*`; при необходимой замене сохранить отдельную датированную копию.
- Проверить Git, uv и требуемый Python по актуальному `mcp/pyproject.toml`. Использовать уже установленные инструменты; недостающее ставить из официальных источников в пользовательскую область. Python сервера не подменять внутренним Python Blender. Не устанавливать Node/Visual Studio/Chocolatey ради этой процедуры.
- Закрепить commit сервера, выполнить актуальную процедуру зависимостей и проверить его команду справки из правильного рабочего каталога. Изменение зависимостей допускается только после подтверждённой несовместимости, с отдельной записью причины и lock-файла в изолированной установке.
- В отдельной локальной папке `blender_mcp_setup` сохранить версии, пути, origin/commit, выполненные команды и точный последний успешный шаг без секретов. Ошибку запуска инструмента Codex отличать от ошибки PowerShell/Blender.

## Шаг 2 — расширение и границы доступа

- Перед настройкой определить доступные средства изоляции. MCP выполняет Python с правами процесса Blender; отдельный `.blend` и адрес localhost не изолируют файловую систему. Не считать отсутствие важных объектов в сцене защитой остальных файлов компьютера. Безопасность среды проверить до первого выполнения кода MCP, без отключения Defender/Firewall или глобальной ExecutionPolicy.
- Пользователь открывает отдельную пустую тестовую сцену. Не закрывать рабочие файлы, не сохранять поверх них и не открывать сцены OSNOVA. Если подтверждённого управления интерфейсом нет, давать по одному действию и ждать результата пользователя.
- По актуальному Setup установить официальное расширение Blender Lab: через официальный репозиторий расширений или корректный ZIP расширения, не ZIP всего исходного репозитория. Проверить автора, manifest и совместимость; сетевой доступ включать только при необходимости с объяснением.
- Запустить мост только на loopback; сверить фактические адрес/порт с текущей документацией. Проверить, что слушающий процесс принадлежит Blender. Не открывать `0.0.0.0`/LAN, не добавлять широкие правила firewall и не завершать неизвестный процесс ради освобождения порта.

## Шаг 3 — подключение Codex и доказательство работы

- Проверить актуальную [документацию Codex MCP](https://developers.openai.com/codex/mcp) и реальное расположение конфигурации с учётом `CODEX_HOME`. До любой правки, в том числе через CLI, сделать датированную резервную копию. Не выводить секреты и не менять другие подключения.
- Команда сервера содержит реальный абсолютный путь к uv, отдельные аргументы рабочего каталога и запуска. Проверить TOML/кодировку/экранирование Windows-путей; не оставлять `~`, `%USERPROFILE%`, `$HOME`, заглушки или дублирующиеся таблицы. Не создавать службу, автозапуск или задачу планировщика: stdio-процессом управляет клиент.
- Последовательно доказать: запуск процесса → MCP initialize/initialized → tools/list со всеми страницами → безопасный запрос к Blender → чтение имён/типов объектов без изменения и сохранения сцены. Проверять `isError` и содержимое ответов; один запущенный процесс не доказывает соединение.
- Отдельно подтвердить доступность инструментов в текущем чате реальным вызовом. Успех самостоятельного диагностического клиента не выдавать за успех инструментов чата. Если требуется перезапуск Codex, сначала согласовать его момент, чтобы не прерывать другую работу; не закрывать Blender автоматически.
- При ошибке зафиксировать точный сбой и последнюю подтверждённую стадию; не объявлять настройку завершённой и не обходить ограничения безопасности.

## Шаг 4 — пробный экспорт и контрольный дом

1. В отдельной пустой тестовой сцене через реально доступные инструменты создать куб и простой материал, экспортировать GLB в `blender_mcp_setup/test_export`. Не сохранять `.blend` автоматически и не переносить результат в OSNOVA. Зафиксировать путь, размер и параметры; это проверка связи/экспорта, не готовности архитектурного адаптера.
2. Отдельной задачей подготовить небольшой контрольный дом по контракту: известные размеры, толщина стен, дверь, окно и высоты; числовые ожидания рассчитаны независимо. Для поддержанных этажей/наружных площадок добавить соответствующий пример, не обещая ещё не реализованную геометрию.
3. Проверить числа, оси, масштаб, ID/revision и реальные отверстия. Просмотреть результат в Blender и целевом браузере; красивый рендер не заменяет проверку геометрии. Повторный запуск не должен дублировать объекты; изменение ревизии должно обновлять результат, не оставляя старые поверхности.
4. Проверить размер/загрузку на целевых устройствах и сохранение доступного 2D при недоступности 3D. Сценарии/контрольные данные сначала остаются локально вместе с генератором; перенос ассетов в сайт и публикация — только в рамках отдельного разрешённого этапа.

Подключение, экспорт куба, приёмка геометрического адаптера и производительность браузерного вида — четыре разных результата. В PROGRESS записывать только реально выполненное, фактические проверки и ограничения. Эта процедура не меняет исходные 119 карточек, зависимости MVP/полной v1 или текущий следующий шаг генератора.
